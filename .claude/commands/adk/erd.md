## Key Rules

### Documentation Principles

1. **No Top-Level Heading**: Do NOT add `# Title` - Lark document title serves as the main heading; start with TTADK quote
2. **Language from Config**: Always use `preferred_language` from `.ttadk/config.json` for language selection, regardless of whether `technical-design.md` exists. Template is for structure reference only.
3. **Conditional Sections**: Only include sections relevant to the changes; omit empty sections entirely
4. **Source Prioritization**: data-model.md > plan.md > spec.md (always document which source was used)
5. **Table Formatting**: Use proper column alignment (`:---` for left, `:---:` for center, `---:` for right)
6. **Diagram Tool Selection**:
   - **Use ONLY Mermaid** for all diagrams: Architecture (graph), flow diagrams (graph TD), sequence diagrams (sequenceDiagram), state diagrams (stateDiagram-v2), ER diagrams (erDiagram)
7. **Language Consistency**: Respect language setting for ALL text output

### Critical Diagram Rules

**USE ONLY MERMAID** for all diagrams in this document. All diagram rules below apply to Mermaid syntax only.

**Target Version: Mermaid 9.1.x** - Use only basic, widely-supported syntax

**Mermaid Flowchart Syntax** (Use `graph` keyword, NOT `flowchart`):

```
graph TD
    A["Node 1"]
    B["Node 2"]
    A --> B
```

**Basic Rules**:
- **Always quote node text**: `A["Text"]`, `B["中文文本"]`
- **Arrow types** (CRITICAL - only these 3 types):
  - `-->` : Solid arrow (normal flow)
  - `-.->` : Dotted arrow (optional/async flow)
  - `==>` : Thick arrow (emphasis)
  - ❌ **FORBIDDEN**: `-,->`, `--x`, `--o`, `-x` (these will cause syntax errors)
- **Arrow labels must be simple**:
  - ✅ Correct: `A -->|Label| B`, `A -.->|旧链路| B`
  - ❌ Wrong: `A -,->|[旧链路]| B` - brackets `[]` cause errors
  - ❌ Wrong: `A -->|<br/>| B` - HTML tags cause errors
  - **Rule**: Labels can ONLY contain letters, numbers, Chinese, spaces, and basic punctuation (`,`, `.`, `-`)
- **Node shapes**:
  - Rectangle: `A["Text"]`
  - Rounded: `A("Text")`
  - Circle: `A(("Text"))`
  - Diamond: `A{"Decision"}`
- **Graph direction**: `graph TD` (top-down) or `graph LR` (left-right)
- **Subgraph syntax** (avoid if possible, use only when necessary):
  ```
  graph TD
      subgraph Title
          A["Node"]
      end
  ```
  - ❌ **DO NOT use brackets in subgraph name**: `subgraph Name[Text]` is WRONG
  - ✅ **Use simple text**: `subgraph Title` or `subgraph "Title with spaces"`
  - Keep subgraphs simple or avoid them entirely

**Mermaid SequenceDiagram Syntax**:

```
sequenceDiagram
    participant A as Client
    participant B as Server
    A->>B: Request
    B-->>A: Response
```

**Alt/Else Conditional Syntax** (for branching scenarios):

```
sequenceDiagram
    participant C as Client
    participant S as Server
    participant DB as Database
    C->>S: Login Request
    S->>DB: Query User
    alt User Found
        DB-->>S: User Data
        S->>S: Validate Password
        alt Password Valid
            S-->>C: Login Success
        else Password Invalid
            S-->>C: Auth Failed
        end
    else User Not Found
        DB-->>S: Empty Result
        S-->>C: User Not Exist
    end
```

**Basic Rules**:
- Use `participant` to define actors with aliases
- Arrow types: `->>` (solid), `-->>` (dotted)
- Keep message text simple
- **Alt/Else syntax**:
  - `alt Condition` starts a conditional block
  - `else Alternative` defines alternative branch
  - `end` closes the alt block
  - Alt blocks can be nested
  - ❌ **FORBIDDEN**: Do NOT use `opt` or `loop` without `end`
  - ✅ **Correct**: Always close `alt`/`else` blocks with `end`

**Mermaid ER Diagram Syntax**:

```
erDiagram
    USER ||--o{ ORDER : places
    USER {
        int id
        string name
    }
    ORDER {
        int order_id
        decimal amount
    }
```

**Basic Rules**:
- For `decimal`: Use `decimal` without parameters (avoid `decimal(10,2)`)
- For `varchar`: Use `string` type

**Relationship Symbols (CRITICAL)**:
- `||--||` : One-to-One (exactly one on both sides)
- `||--o|` : One-to-Zero-or-One (one side required, other side optional)
- `||--o{` : One-to-Many (one required, many optional)
- `||--|{` : One-to-Many (one required, at least one on many side)
- `}o--o{` : Many-to-Many (both sides optional)

**Symbol Breakdown**:
- `||` = Exactly one (required)
- `o|` = Zero or one (optional single)
- `|{` = One or more (required multiple)
- `o{` = Zero or more (optional multiple)

**Relationship Writing Rules** (CRITICAL):

1. **Always write from LEFT to RIGHT**: `LeftEntity ||--o{ RightEntity`
2. **Left side symbols**: `||` (exactly one) or `}o` (zero or more) or `}|` (one or more)
3. **Right side symbols**: `||` (exactly one) or `o|` (zero or one) or `o{` (zero or more) or `|{` (one or more)
4. **Read as**: "LeftEntity [has] RightEntity"

**Relationship Examples**:

| Scenario | Correct Syntax | How to Read |
|:---------|:---------------|:------------|
| One-to-One | `USER \|\|--\|\| PROFILE` | User has exactly one Profile |
| One-to-ZeroOrOne | `USER \|\|--o\| AVATAR` | User has zero or one Avatar |
| One-to-Many | `USER \|\|--o{ ORDER` | User has zero or more Orders |
| One-to-AtLeastOne | `ORDER \|\|--\|{ ORDER_ITEM` | Order has one or more OrderItems |
| Many-to-Many | `USER }o--o{ ROLE` | Users and Roles (many-to-many) |

**Non-Database Scenarios (Classes/Objects)**:
For C++/Java class relationships, memory structures, or object models:
- Use ER diagram to show **ownership** and **composition** relationships
- `||--||` : Strong composition (child cannot exist without parent)
- `||--o|` : Optional composition (parent may or may not have this component)
- `||--o{` : Collection ownership (parent owns zero or more children)
- `||--|{` : Required collection (parent must have at least one child)

**Example - Class Relationships**:
```
erDiagram
    Processor ||--|| VideoNode : "owns"
    Processor ||--|| AudioNode : "owns"
    Processor ||--|| TrackManager : "owns"
    TrackManager ||--o{ TrackHandle : "manages pool"
    TrackHandle ||--|| TrackConfig : "uses"
```

**Attribute Comments**:
- Always add comments to explain each attribute
- Format: `type name "comment"`
- Keep comments concise (under 20 chars) for single-line display on Lark

**Mermaid StateDiagram Syntax**:

```
stateDiagram-v2
    [*] --> State1
    State1 --> State2
    State2 --> [*]
```

**Basic Rules**:
- Use `stateDiagram-v2` keyword
- Simple state transitions with `-->`
- Use `[*]` for start/end states

**Highlight Changes**:
- Apply styles AFTER diagram: `style NodeName fill:#ff6b6b`

### Change Documentation

1. **Diff Format**: Use `-` and `+`, add `-- 🔴 Change: <explanation>` for key changes
2. **Flat Structure for Core Changes**: Each interface uses ONE `### 4.x` heading only
   - NO sub-headings like `#### 4.1.1 Main Flow` - combine all flows into one comprehensive diagram
   - Flowchart should include: main path, branches, error handling in ONE diagram
   - Sequence diagram should use `alt/else` for different scenarios
3. **Async Flows as Separate Sections**: MQ consumers and background jobs get their own `### 4.x` section
4. **Language Consistency**:
   - **CRITICAL**: ALL content must be in ONE language based on `preferred_language` setting
   - 'zh' → ALL text in Chinese (section titles, diagram labels, table content, descriptions)
   - 'en' → ALL text in English
   - **DO NOT mix languages** - no bilingual labels

### Error Handling

1. **No design artifacts found**: ERROR "Cannot generate TDD without at least spec.md or plan.md. Please run `/adk:specify` first."
2. **Insufficient information for a section**: Omit that section entirely rather than marking "To be supplemented"
3. **Invalid diagram syntax**:
   - Run self-check on all Mermaid code blocks before writing file
   - Common issues to fix:
     - Unquoted node text → Add quotes: `A[Text]` → `A["Text"]`
     - Wrong arrow syntax → Replace: `-,->` → `-.->`, `--x` → `-->`
     - Complex labels → Simplify: `[旧链路]` → `旧链路`, `<br/>` → remove
     - Subgraph brackets → Remove: `subgraph Name[Text]` → `subgraph Name`
   - If syntax cannot be simplified, use text description instead of diagram
4. **Conflicting information**: Prioritize data-model.md > plan.md > spec.md, document conflict in notes
5. **Lark upload failed**:
   - Ensure local file `FEATURE_DIR/technical-design.md` is generated successfully first
   - Report the error in completion summary with message: "Lark upload failed: [error details]. Local file generated successfully. Please upload manually."
   - Do NOT fail the entire command - local document generation is the primary deliverable
